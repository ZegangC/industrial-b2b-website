# 案例：让工业买方从查资料走到可跟进的咨询

[English case](case-study.en.md) · 阅读约 4 分钟 · 2026-10-21 回顾整理

## 1. 概览

| 项目要素 | 实际情况 |
| --- | --- |
| 场景 | 工业材料企业的海外产品、信任资料与询盘承接 |
| 我的职责 | 需求与素材输入、范围讨论、业务判断、多轮评审与推进；AI 辅助实现 |
| 协作边界 | 正式团队角色、审批人与个人开发工时未完整核实，不虚构产品团队规模 |
| 记录时间 | 2026-10-10 至 10-13 留存本地迭代记录；10-15 整理公开版本 |
| 当前阶段 | 本地可评审；生产收件与销售通知待联调，AI 客服未实现 |
| 公开交付 | 产品案例、买方路径、精选询盘/TDS规则与离线测试；完整网站未公开 |

此案例为补充项目，展示产品路径和交付边界。[证据索引](evidence-map.md)区分业务要求、本地实现和公开模拟验证。

## 2. 问题：买方要做决定，网站要接住真实需求

企业希望把社媒、搜索、广告或销售分享带来的访问，承接到产品与品牌信息中心。买方可能先核实供应商，也可能直接查材料、应用或技术资料。

这些是业务目标和待验证的买方任务，不是既有转化漏斗的实测结论。没有基线数据时，不能先假定旧站转化差，更不能承诺改版会带来多少询盘。

已有约束包括：产品信息必须有审核依据，不公开内部型号和价格；多处咨询入口需要带入上下文；首期应能把需求交给业务，而不是先建设完整CRM。

## 3. 过程：明确需求来源，逐步限制首期范围

业务要求逐步形成了经销商优先、主推材料与核心应用、多语、产品和可信度展示等方向。我的工作是提供和核对业务材料、参与这些范围判断，持续评审内容与交互；代码和文档由AI工具辅助生成。

项目记录包括旧站素材盘点及同行目录研究，重点借鉴应用、产品和资料入口之间的关系。它们不是对真实买方访谈的替代，也不能直接证明同行的路径适合本项目。

| 需要决定的事 | 当前选择 | 代价和验证问题 |
| --- | --- | --- |
| 多页面如何收集需求 | 多个CTA带上下文进入同一表单 | 维护一套流程；要验证产品、语言和来源是否正确带入 |
| 什么才可以显示提交成功 | 校验接收端明确保存且提交ID匹配 | 接口200不够；生产持久化、通知和补偿仍需联调 |
| 资料是否都需留资 | 已实现指定TDS的申请与授权路径 | 便利与线索收集有取舍；尚无实验支持“门槛越多越好” |
| 是否优先增加AI客服和CRM | 先完成内容与人工承接，保留后续边界 | 无即时AI答疑；后续以真实问题量和知识质量决定投入 |

上述取舍是对实现和讨论记录的回顾，不把AI建议全部归为个人原创决策，也不虚构正式立项或用户研究流程。

## 4. 方案：一个面向买方、一个面向接收可靠性的流程

![买方浏览到统一咨询与资料授权的示意](../assets/buyer-journey.svg)

本地业务站已有中英葡三语、产品检索与筛选、主推资料对比、企业与内容页面、统一询盘和TDS申请。语言路由与翻译实现仍需目标市场和技术术语审校。

公开仓库提供其中的核心规则：[字段与收件校验](../src/lib/inquiry.ts)、[资料授权与本地保存](../src/lib/tds-access.ts)。运行演示依次观察“未配置”“200但无回执”“匹配保存回执”三种结果。响应由内存模拟提供，没有真实通知销售；详见[实现范围](implementation-scope.md)。

## 5. 结果：可评审的本地交付，运营效果待测

| 结果 | 来源与日期 | 解释范围 |
| --- | --- | --- |
| 三语共171内容页、17族产品检索、两主推对比 | v0.17，2026-10-13 原项目验收记录 | 模板与内容覆盖，不是线上流量或独立功能数 |
| 原业务站18项测试通过 | 2026-10-15 本地评估时重跑 | 当次询盘、内容、多语和TDS部分规则 |
| 精选模块可独立测试和演示 | 本仓库代码与测试 | 对公开规则分支的可复验检查，非全站端到端验收 |
| 正式询盘、销售跟进、转化与SEO效果 | 尚无本次可核验运营结果 | 不报告增长、收入或排名提升 |

业务站未部署，生产可靠保存和业务通知未联调。公开模块附带提交ID，不意味着生产接收系统已完成持久化去重；签名资料链接也不是账户鉴权或防转发机制。

## 6. 复盘：先验证买方任务，再扩展内容与自动化

项目已经积累了较多页面，但缺少真实用户任务测试。若重新安排，我会更早选择少量代表路径，观察买方能否找到合适方向、理解资料限制并提交需求，而不是以页面增长代替产品价值。

下一步先做少量业务人员/相关买方的任务测试，记录卡点与改动，再完成收件和通知联调。正式运行后，分开观察入口点击、确认保存、人工判定有效、回复和订单。AI客服以审核知识、人工接管和真实服务负担为前提，另行验证。
